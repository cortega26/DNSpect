## Why this matters

The checked-in locks are the dependency inputs used by local development, CI,
and release packaging. A lock-only audit at this commit reports 12 Python
vulnerabilities in Starlette, idna, and python-multipart, and eight npm
vulnerabilities including a critical Vitest issue and high-severity Vite and
transitive build-tool issues. This plan updates compatible direct toolchain
owners, regenerates both locks reproducibly, and makes those two lock-only
audits release gates so a stale lock cannot silently re-enter the product.

## Current state

- `backend/pyproject.toml` — authoritative backend runtime, dev, and packaging
  dependency declarations; declares Python 3.13+.
- `backend/constraints.txt` — pip-compile output used for backend installs and
  release packaging, but its header was generated with `dev` only.
- `frontend/package.json` and `frontend/package-lock.json` — frontend tooling

- `Makefile` — the established local quality-gate entry point.

## Steps

### Step 1: Replace vulnerable Python framework owners with the verified compatible releases

In `backend/pyproject.toml`, replace the vulnerable direct framework pins with
the compatible set verified during planning:

- `fastapi==0.141.1`
- `starlette==1.6.0`
- `python-multipart==0.0.32`

Add `pip-audit==2.10.1` to the `dev` optional dependency group so the local
development environment can run the audit command that CI will require. Keep
the existing Python 3.13 floor, `httpx`, package extras, and all non-audit
runtime pins unchanged. Do not add `idna` as a direct runtime dependency: it
is an indirect dependency that the compiled lock must resolve to exactly
`idna==3.18` (which is above the 3.15 fixed floor).

First run the resolver command in the table above. If it reports a FastAPI /
Starlette conflict, do not downgrade Python, loosen exact pins, or force an
incompatible wheel; stop and report the resolver output.

**Verify**: `cd backend && python3.13 -c "import tomllib; p=tomllib.load(open('pyproject.toml','rb')); print(p['project']['requires-python']); print(' '.join(p['project']['dependencies'])); print(' '.join(p['project']['optional-dependencies']['dev']))"` → output includes `>=3.13`, `fastapi==0.141.1`, `starlette==1.6.0`, `python-multipart==0.0.32`, and `pip-audit==2.10.1`.

### Step 2: Regenerate and audit the complete Python constraints lock

From a Python 3.13 environment, regenerate `backend/constraints.txt` from the
modified project file using the exact command in the commands table. The
compiled input must include **both** `dev` and `pack`, because CI and release
install those two different extras. Retain pip-compile's generated header; it
must name `--extra=dev --extra=pack`, not the current dev-only command.

Review the resulting lock before continuing. It must contain exact direct and
transitive pins for the updated framework, `python-multipart==0.0.32`,
`idna==3.18`, `pip-audit==2.10.1`, and `pyinstaller==6.16.0`. Do not manually
edit individual generated entries or retain an old vulnerable transitive pin.

Install the project in a fresh Python 3.13 virtual environment using the new
constraints and run `pip-audit` against the file itself. The audit must cover
the lock, not only whatever happens to be installed in the executor's shell.

**Verify**: `rg -n '^(fastapi==0\.141\.1|starlette==1\.6\.0|python-multipart==0\.0\.32|idna==3\.18|pip-audit==2\.10\.1|pyinstaller==6\.16\.0)$' backend/constraints.txt && pip-audit -r backend/constraints.txt --no-deps --progress-spinner off` → every requested pin is printed; audit exits 0 with `No known vulnerabilities found`.

### Step 3: Upgrade the audited frontend developer toolchain and refresh its lock

Update only frontend **developer tooling** in `frontend/package.json`; leave
React, React DOM, Recharts, and application source dependencies unchanged.
Use these reviewed direct versions, retaining the repository's caret-style
range convention where npm writes it:

- `@eslint/js` 10.0.1 and `eslint` 10.8.1
- `@typescript-eslint/eslint-plugin` and `@typescript-eslint/parser` 8.67.0
- `eslint-plugin-react-hooks` 7.1.1, `eslint-plugin-react-refresh` 0.5.4,
  and `globals` 17.9.0
- `@vitejs/plugin-react` 6.0.5, `vite` 8.2.1, and `vitest` 4.1.10

Regenerate `frontend/package-lock.json` using `npm install --package-lock-only
--ignore-scripts`; never run `npm audit fix --force`. Ensure the lock's root
package version becomes the declared `1.2.0`, eliminating the current `1.0.1`
mismatch. Then use `npm explain --package-lock-only` for any remaining audited
transitive to identify its direct owner. Prefer an owner upgrade within this
toolchain set; add a targeted `overrides` entry only if the owner cannot yet
release a safe compatible range, and document that exact owner/range in the
commit message.

If Vite 8 or ESLint 10 requires a documented configuration migration, make the
smallest compatible change in `frontend/vite.config.ts` or
`frontend/eslint.config.js` respectively. Do not change components, tests, or
application behavior to accommodate a tool upgrade.

**Verify**: `cd frontend && node -e "const fs=require('node:fs'); const p=JSON.parse(fs.readFileSync('package.json')); const l=JSON.parse(fs.readFileSync('package-lock.json')); if (p.version !== l.packages[''].version) process.exit(1); console.log('lock-root-version=' + l.packages[''].version)" && npm audit --package-lock-only` → prints `lock-root-version=1.2.0`; audit exits 0 with `found 0 vulnerabilities`.

### Step 4: Make lock-only audits first-class local, CI, and release gates

Add a `dependency-audit` Make target that runs exactly these two commands in
order:

1. `cd backend && . .venv/bin/activate && pip-audit -r constraints.txt --no-deps --progress-spinner off`
2. `cd frontend && npm audit --package-lock-only`

In `.github/workflows/ci.yml`, add a dedicated Ubuntu `dependency-audit` job.
It must check out the repository, set up Python 3.13 and Node 24, install
`pip-audit==2.10.1` constrained by `backend/constraints.txt`, then execute the
same Python lock audit and frontend `--package-lock-only` audit. Do not replace
the existing backend/frontend test jobs.

In `.github/workflows/release.yml`, add the same single Linux
`dependency-audit` job and make the matrix `build` job depend on it. This
ensures a tag cannot publish a binary from a lock that CI would reject, while
avoiding three redundant network audit jobs in the platform matrix. Keep the
existing `publish` dependency on `build`; it will transitively wait for the
audit.

**Verify**: `make dependency-audit && rg -n 'dependency-audit|pip-audit -r backend/constraints.txt --no-deps|npm audit --package-lock-only|needs: dependency-audit' Makefile .github/workflows/ci.yml .github/workflows/release.yml` → audit target exits 0; grep shows one CI audit job, one release audit job, and the release build dependency.

## STOP conditions

Stop and report back if:

- FastAPI 0.141.1 and Starlette 1.6.0 no longer resolve together on Python
  3.13, or their compatibility tests require endpoint/schema/application
  behavior changes outside the narrowly permitted config files.
- The regenerated Python lock contains a vulnerability without a fixed
  version, or remediation requires changing the declared Python floor.
- `npm audit --package-lock-only` still reports a vulnerability after updating
  the named direct toolchain owners and the remaining fix would require an
  unreviewed major application/runtime dependency change or a broad override.
- Vite 8 or ESLint 10 requires changes outside `frontend/vite.config.ts` or
  `frontend/eslint.config.js` to make the app build or test.
- A generated Flatpak module/source file changes while running this plan; revert
  that incidental generated output and leave it to plan 012.
- Any final quality gate fails twice after a reasonable in-scope correction.
